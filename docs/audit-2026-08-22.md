### Session B — `GridManager`-Klasse extrahieren

**Modell-Empfehlung:** Sonnet 4.6 · medium
**Scope:** Refactoring, kein Gameplay-Wechsel. Multi-Shelf-Modell bleibt.
**Definition of Done:** Layout-Berechnung lebt in einer eigenen Klasse; `GameScene` und `Shelf` kennen nur noch eine `GridManager`-API.

#### Schritte

1. **Klasse `GridManager` in `src/main.ts` einführen** (gleiche Datei, neue Section zwischen Section 4 und 5)
   - Übernimmt: `gridTop`, `gridBottom`, `shelfSpacing`, `shelfWidth`, `startY`, `itemScale`, `LEVEL_BG_KEYS`-Lookups.
   - API:
     ```ts
     class GridManager {
       constructor(scene, level);
       getRowY(row: number): number;
       getRowWidth(): number;
       getItemScale(): number;
       getShelf(row: number): Shelf;        // baut Shelf on-demand
       getBgKey(): string | undefined;
     }
     ```
   - Quelle für `gridTop/gridBottom/shelfSpacing/startY`: aktuell in `GameScene.buildLevel` (`src/main.ts:1083-1093`).

2. **`GameScene.buildLevel` reduzieren** auf:
   ```ts
   this.grid = new GridManager(this, level);
   this.shelves = this.grid.buildAll();
   ```
   Schleife über `level.layout.forEach` fliegt raus.

3. **`onPointerDown` (`src/main.ts:1100-1164`) entkoppeln**
   Aktuell rechnet die Hit-Test-Logik `localX`, `slotIdx` und Shelf-Koordinaten selbst. Sollte via `GridManager.shelfAt(x, y)` und `GridManager.slotAt(shelf, localX)` laufen. `Shelf.slots[slotIdx]` bleibt in `Shelf`, der Hit-Test delegiert aber nach oben.

4. **Z-Order im Container**
   `Shelf` setzt aktuell keinen expliziten `depth`. Spätere Session C braucht Z-Order für „Item fliegt aus dem Grid in den Tray" — der Tray soll über dem Grid liegen, das angeklickte Item kurz vor dem Tray. `GridManager` kann `this.bgLayer.setDepth(-10)`, `this.gridLayer.setDepth(0)`, `this.trayLayer.setDepth(10)` setzen — auch wenn der Tray erst in C kommt.

#### Verifikation
- `npm run build` typenrein.
- Visuell keine Änderung (gleiches Layout).
- `git diff --stat src/main.ts` zeigt: `GameScene` schrumpft, `GridManager` wächst; netto leicht mehr Code, klarere Struktur.

### Session C — 7-Slot-Tray-Umbau (Gameplay-Wechsel)

**Modell-Empfehlung:** Opus · high
**Scope:** Echter Gameplay-Wechsel. Berührt `LEVELS`, `GameScene`, `Shelf`, `UI`, Win/Loss, Booster.
**Definition of Done:** Briefing wörtlich umgesetzt — ein Tray mit 7 Slots am unteren Rand, Items fliegen vom Grid in den Tray, 3er-Match triggert FX, Danger-Pulse bei 5/6 Slots.

**Wichtig:** Diese Session steht unter Vorbehalt — das aktuelle Multi-Shelf-Modell ist ein anderes (valides) Spiel. Vor dem Start mit dem User bestätigen, dass das Briefing die Multi-Shelf-Variante komplett ersetzt und nicht ergänzt.

#### Schritte (Übersicht — Detail-Planung erst beim Start)

1. **`LEVELS`-Datenmodell wechseln**
   Alt: `layout: SlotData[][]` (Reihe × 3 Slots mit `front`+`queue`).
   Neu: `items: { row: number; col: number; itemId: string }[]` — flache Liste von Startpositionen pro Item. Beispiel:
   ```ts
   {
     moves: 16,
     targetMatches: 8,
     items: [
       { row: 0, col: 0, itemId: 'ichigo_daifuku' },
       { row: 0, col: 1, itemId: 'ichigo_daifuku' },
       { row: 1, col: 0, itemId: 'inarizushi' },
       // ...
     ]
   }
   ```
   3er-Match muss aus der Verteilung der Item-IDs ableitbar sein, dass es überhaupt lösbar ist (Solver-Check post-generieren).

2. **`Shelf` ersetzen durch `Grid` + `Tray`**
   - `Grid`: berechnet Positionen aus `items: [...]` Liste, baut `GoodsItem`-Container, kein internes Match mehr.
   - `Tray`: 7 Slots, fixe Breite über Canvas, am unteren Rand, hält 0–7 Items, `checkMatch()` schaut die letzten 3 Slots und löst FX aus, dann komprimiert.

3. **Klick-Logik in `GameScene.onPointerDown`**
   - Klick auf Grid-Item: nimm es aus dem Grid auf, fliege per `Phaser.Curves.QuadraticBezier` zum ersten freien Tray-Slot. Beim Eintreffen: `Tray.checkMatch()`.
   - Klick auf Tray-Item: nur erlaubt, wenn es das **vorderste** ist (Slot 0 oder das am weitesten links belegte). Vereinfachtes Push-Back in den nächsten freien Grid-Slot — oder gar nicht erlaubt (war im Briefing nicht explizit, ggf. mit dem User klären).
   - Hammer-Booster: gezielt ein Grid-Item entfernen, kein Tray-Item zerstören (würde 3er-Match-Logik umgehen).

4. **Danger-Pulse**
   - `Tray` registriert seine Belegung. Bei 5 oder 6 Slots: kontinuierlicher Tween auf dem Tray-Background (`scale 1.0 ↔ 1.04`, 600 ms `Sine.easeInOut`, yoyo).
   - Bei 7 Slots ohne sofortiges Match: `Game Over`-Modal.
   - Korreliert mit kurzem `playTap`-ähnlichem Cues in `ZenAudioEngine` — neuer `playDanger()`.

5. **Win/Loss**
   - Win: alle Grid-Items weg, Tray leer.
   - Loss: Tray voll (7/7), kein Match ausgelöst.
   - Aktuelle `WinModalScene` (`src/main.ts:1412-1466`) hat nur Win — `LoseModalScene` (oder gleicher Modal mit `LOSE`-Variante) nötig.

6. **`@fontsource` Danger-Sound optional**
   `ZenAudio.playDanger()` als neue Methode, kurzer 2-Ton-Sweep, Vibrate `[20, 60, 20]`.

#### Verifikation
- `npm run build` typenrein.
- Level 1–6 spielbar, jedes lösbar.
- Bei 5/6 Tray-Slots pulst der Tray-Hintergrund.
- Bei 7/7 ohne Match erscheint `LoseModalScene`.
- Danger-Pulse stoppt, sobald ein 3er-Match den Tray leert.
